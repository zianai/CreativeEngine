# P9 — failure boundaries and compatibility

P9-00 prioritizes concrete P8/P7 safety gaps without claiming a real pilot. P9-CE-01 exercises distinct real process death points: before provider invocation, after simulated acceptance without receipt, after durable image/receipts before DB commit, and after Vision begins without its semantic receipt. A synthetic provider is explicitly a fault instrument, never live model proof. Response-then-storage failure and receipt-field deletion have separate regression cases. No new image is generated when outcome is ambiguous.

P9-CE-02 keeps deterministic rights/fidelity and QA authoritative; an injected synthetic Vision “pass” cannot override revoked rights. Skipped Vision remains skipped and pending human review. Genuine calibration against two human reviewers is BLOCKED_EXTERNAL. P9-CE-03 retains unknown actual bill/null, separates estimate/unknown liability and never automatically enables provider-native batch. One-shot E2 image command has grant-bound preflight and no-credential denial tests; fresh live execution is blocked.

P9-CONTRACT-01 adds a frozen LaunchCase consumer artifact, independent actual CE HTTP provider verification, additive-field compatibility and missing-QA/wrong-unit negatives. Historical visual-task 1.0.0 bytes are preserved. P9-OPS-01 adds loopback auth/session, current-rights/hash export gates, error minimization, write quotas, process state monitoring and restore. P9-UX-01 retains the visual design and makes local session/approval meaning explicit; actual backend browser captures cover pending/approved and unknown-cost states. Human visual sign-off is still design_pending.
