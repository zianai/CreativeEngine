# Skills and deterministic planning

Skills are installed as local directories whose manifest `id` is a bounded lowercase slug. Adding a Skill directory does not require modifying the engine or its workflow enum. Each built-in Skill has a versioned manifest, readable method, JSON input schema, prompt template, QA profile and runnable brief example. `loadSkills()` validates all four manifests at startup. `createPlan()` parses a brief without making a model call or incurring cost. Its deterministic VisualIntentRouter uses product stage, requested changes, delivery target, fidelity and authorized original sources.

`VisualPlan` is an immutable production decision. It stores the exact Skill version, prompt template and QA rules plus a SHA-256 digest. The compiler reads this saved snapshot, so changing an installed Skill does not silently change queued work. The current deterministic source/claim policy is still checked before execution. Historic content is never authority to bypass that policy.

Strict real SKU work uses only reuse or deterministic composition. A verified product photo or cutout and the exact Product Truth snapshot are required. Original source records may support facts; generated and derived assets cannot. A truth fact retains its evidence status and source version. External claims must match a verified, external-allowed fact exactly. A technical claim detected in a free-form existing-SKU brief without matching evidence blocks execution. This lexical guard is intentionally conservative; it is not a complete natural-language fact checker. Factual text is compiled only from explicit validated claims, with human review required.

A plan may select `background_asset_id` for deterministic scene composition. It must identify an authorized source of kind `reference` or an approved generated concept in the same project. A verified transparent product cutout and explicitly permitted background change are required. Mock and unreviewed backgrounds are rejected. An approved generated background is a visual layer only and can never become Product Truth evidence.

Controlled customization requires an explicit allowed-change list, preserves product identity, and carries a deterministic Concept / For Review label. Color changes on verified transparent cutouts and layout/logo changes use deterministic composition; color changes without a cutout and texture/material/finish changes route to reference editing and require a capable provider. An existing SKU cannot enter exploratory mode. Create a separate concept product for structural exploration. Concept planning creates distinct industrial-design directions from each Skill; those directions and the original constraints survive into every compiled prompt.

All entity protocols are versioned through `packages/contracts`; the OpenAPI document links those same schemas to HTTP requests and responses. Export manifests distinguish `audience: internal` from `audience: external`. The external schema allows only verified, externally cleared facts and deliberately omits prompt text, internal requirements and reviewer notes.

Domain-specific structured inputs live under `CreativeBrief.skill_input` (up to 128 keys and 64 KiB serialized). A Skill JSON Schema validates the complete normalized brief, including this extension object, using Ajv 2020-12. Remote or filesystem `$ref` values and asynchronous validation are rejected; only local fragment references are supported. The immutable plan captures the schema and declared defaults along with the prompt and QA profile. Runtime execution validates the saved schema again, so changing an installed template or schema cannot alter queued work. Global source, truth, fidelity and approval rules take precedence over any Skill default.

The current Creative Planner is a transparent rule-based planner, not an autonomous LLM agent. `validateAgentPlan()` is the structured adapter boundary for a future planner model: output must satisfy the same Zod schema and source policy. This keeps budget, truth and approval decisions out of model control. `compilePrompt()` emits auditable text and structured constraints. Vision QA is independently provided by the quality package.

To add or revise a built-in Skill:

1. Choose a safe lowercase slug and supply `SKILL.md`, `skill.yaml`, `schemas/input.schema.json`, `prompts/production.txt`, `qa-rules/default.yaml` and a realistic example.
2. Increment the semantic version for changes to behavior, prompts or QA criteria. Never overwrite saved plans.
3. Validate with `loadSkills()` and add policy tests for the new behavior.
4. Keep template resources relative to the Skill folder. Absolute paths and traversal are rejected.

Platform policy is not hardcoded as model knowledge. `packages/planner/delivery-rules.ts` loads versioned YAML data from `rules/`. Every rule records its source, source date and scope (`user_defined` or `official`). A brief can select `delivery_rule_id`; the plan stores the full digest-protected snapshot and blocks incompatible aspect ratios. Quality checks enforce configured minimum dimensions, formats, byte limit and aspect ratio. The included `custom-square` profile is an operator-defined sample, not a marketplace policy. No current Amazon, eBay or other official platform rule bundle has been verified or shipped; an official bundle must cite its authoritative HTTPS source and its applicability must be checked by the operator.
